1.1What file I/O is

File I/O means Input/Output: how Python reads data from a file on disk and writes data back to one.

f = open("test_file.txt", "r")

open() gives you back a file object. It's an object, so it has methods (things it can do, like .read()) and properties (facts about it, like .closed).

ArgumentMeaning
nameThe file name or path, e.g. "data.csv"
access_modeWhat you want to do: read, write, append…
bufferingHow much of the file is held in memory at once. You rarely set it.
ModeWhat it does
'r'Read. This is the default.
'w'Write. Wipes the file first.
'a'Append. Adds to the end and keeps old content.
'x'Create a new file. Fails if it already exists.
'b'Binary, for images and other non-text files.
'+'Read and write.

2.1What JSON is

JSON (JavaScript Object Notation) is a text format for storing and sending data. It looks almost exactly like a Python dictionary.

{
  "name": "John",
  "age": 30,
  "emails": ["john@example.com", "john@gmail.com"],
  "address": {"street": "123 Main St", "city": "Exampleville"}
}
JSONPython
Object { }dict
Array [ ]list
String / numberstr / int or float
true / falseTrue / False
nullNone
Why it exists: a CSV is flat, with one value per cell. JSON can nest: John has two emails and an address with its own parts.

2.2dump, dumps, load, loads

FunctionDirectionWorks with
json.dumps(obj)Python → JSONgives back a string
json.dump(obj, file)Python → JSONwrites into a file

Memory trick: dump = save out, load = bring in, and the "s" means string. Python → JSON is serializing, and back is deserializing.

6.2A subquery that returns a single value

Start with a hard-coded filter:

SELECT `COMMUNITY NAME`, `LICENSE VOLUME`
FROM workspace.default.licensed_pets
WHERE `LICENSE VOLUME` > 34

Where did 34 come from? Someone worked it out by hand. If the data changes, it goes stale, and nobody reading the query knows what it means. Let a query calculate it instead:

SELECT `COMMUNITY NAME`, `LICENSE VOLUME`
FROM workspace.default.licensed_pets
WHERE `LICENSE VOLUME` > (
    SELECT AVG(`LICENSE VOLUME`) FROM workspace.default.licensed_pets
);
1. Inner queryRuns first. AVG with no GROUP BY collapses the table to one number, e.g. 250.24.
2. SwapSQL effectively replaces the brackets with that number: WHERE LICENSE VOLUME > 250.24.
3. Outer queryReturns only the above-average rows.

The inner query has to run first because the outer WHERE can't filter until it knows the number it's comparing against.

Remember: > compares against one value, so the subquery must return exactly one row and one column (a scalar subquery). Add GROUP BY ANIMAL inside and it returns 2 rows, which raises "subquery returned more than one value".

6.3A subquery that returns a list: IN

IN keeps a row if its value matches any item in a list. It's shorthand for several ORs. A hard-coded list has the same problem as the hard-coded 34, so build the list with a query:

SELECT * FROM workspace.default.licensed_pets
WHERE `COMMUNITY NAME` IN (
    SELECT `COMMUNITY NAME`
    FROM workspace.default.licensed_pets
    GROUP BY `COMMUNITY NAME`
    HAVING SUM(`LICENSE VOLUME`) > 500
);
GROUP BY COMMUNITY NAMEOne group per community (cats and dogs together).
SUM(LICENSE VOLUME)Adds cats and dogs within each community.
HAVING ... > 500Keeps only communities whose total is above 500.
SELECT COMMUNITY NAMEOutputs one column, many rows: the list.

The subquery only decides which communities qualify. The outer query then returns every original row for them. If Acadia has 478 cats and 300 dogs (778 > 500), both Acadia rows come back: 2 rows.

WHEREFilters individual rows, before grouping. SUM(...) doesn't exist yet, so WHERE SUM(...) > 500 fails.
HAVINGFilters groups, after aggregation. If the condition uses SUM, AVG or COUNT, it goes here.
Trap: if a NOT IN list contains even one NULL, NOT IN returns no rows at all. Filter out NULLs in the subquery or use NOT EXISTS.

6.4A subquery that returns a table, and CTEs

Question: for cats vs dogs, what's the average number of licences per community? That needs two levels: SUM per animal per community, then AVG of those sums. AVG(SUM(...)) isn't allowed, so do the first step in a subquery in FROM (a derived table):

SELECT ANIMAL, AVG(total) AS avg_community_total
FROM (
    SELECT ANIMAL, `COMMUNITY NAME`, SUM(`LICENSE VOLUME`) AS total
    FROM workspace.default.licensed_pets
    GROUP BY ANIMAL, `COMMUNITY NAME`
) AS community_totals
GROUP BY ANIMAL;
Inner queryOne row per animal + community. With 200 communities that each have both animals: 400 rows.
Outer queryGroups by animal and averages total: 2 rows. (Grouping collapses rows; filtering removes them.)
AS totalNames the sum so the outer query can refer to it.
AS community_totalsNames the derived table. Most databases, including SQL Server, require it.

Filtering on a derived table works with plain WHERE, even on a sum:

SELECT customer_id, total_amount
FROM (
    SELECT customer_id, SUM(amount) AS total_amount
    FROM orders
    GROUP BY customer_id
) AS t
WHERE total_amount > 400
ORDER BY customer_id;

It works because the sum was already calculated inside. To the outer query, total_amount is just an ordinary column.

    FROM workspace.default.licensed_pets
    GROUP BY ANIMAL, `COMMUNITY NAME`
)
SELECT ANIMAL, AVG(total) AS avg_community_total
FROM community_totals
GROUP BY ANIMAL;

6.6Window functions: OVER and PARTITION BY

7.7Writing an aggregate: what it reveals

DELIMITER //

CREATE AGGREGATE FUNCTION my_sum(x INT)
RETURNS INT
BEGIN
  DECLARE total INT DEFAULT 0;
  DECLARE CONTINUE HANDLER FOR NOT FOUND RETURN total;
  LOOP
    FETCH GROUP NEXT ROW;                -- next row of the group
    IF x IS NOT NULL THEN
      SET total = total + x;
    END IF;
  END LOOP;
END //

DELIMITER ;
An aggregate is a loop with a running state. It reads a group one row at a time, keeps a small memory, and returns one value when the rows run out.
AggregateRunning stateUpdate on each non-NULL row
SUMtotal, starts at 0total = total + x
COUNTcount, starts at 0count = count + 1
MAXbiggest, starts NULLif NULL or x > biggest, biggest = x
Why skip NULLs?total + NULL = NULL, and it stays NULL, so one missing value would wipe out the whole group's sum.
Why rows collapseIt returns only once per group, at the end.
Why no AVG(SUM(x))That would be a loop inside a loop over the same rows; use a subquery or CTE.
Big dataSUM, COUNT, MIN, MAX need one pass and little memory, and partial results from different machines can be combined. AVG = SUM ÷ COUNT, so it combines too. A median can't, so it's expensive at scale.

9.1Keys and primary keys

The problem: how do you guarantee every row is unique? Two "Ava Smith" rows could be one student entered twice or two different students, and then you can't safely update, delete or count them.

A key is a column where every value is different, like a library card number. Keys are usually not allowed to be NULL: a blank can't identify anything.

StrategyHowExample
Composite keyNo single column is unique, but a combination islicensed_pets: community + animal + date
Counter (surrogate key)The database numbers rows 1, 2, 3…MariaDB AUTO_INCREMENT; SQL Server IDENTITY(1,1); MongoDB's _id

Things often have several candidate keys (a car: plate, VIN). The table picks one as its primary key.

Student table optionUnique?Never blank?Never changes?
Name❌✅❌
Email✅ usually❌❌
Student ID✅✅✅
Remember: a good primary key is unique, never blank, and never changes. "Never changes" matters because other tables point at it. For cars, pick the VIN: plates change when a car is sold or moves province.
CREATE TABLE student (Student_ID INT PRIMARY KEY, Name VARCHAR(50));
INSERT INTO student VALUES (2, 'Dan');      -- ok
INSERT INTO student VALUES (2, 'Dan');      -- ❌ rejected: ID 2 exists (only the key is checked)
INSERT INTO student VALUES (NULL, 'Cara');  -- ❌ rejected: key can't be NULL

Those automatic checks are constraints. MongoDB let in duplicates and text years because nothing enforced rules. Before querying, work out what one row means (its key): it tells you what COUNT(*) counts and what to group or join on. community_name alone can't key licensed_pets, because each community appears on many rows (one per animal per date).

9.2Foreign keys

A foreign key is a column that points to another table's primary key, like a loans table storing a library card number instead of copying the member's details.

members                     loans
card_no (PK) | name         loan_id (PK) | card_no (FK) | book
1001         | Ava   ◄────  1            | 1001         | Dune
1002         | Ben   ◄────  2            | 1002         | Emma
                     ◄────  3            | 1001         | Ulysses

Benefits: details are stored once, there's one place to update, and joins are easy.

CREATE TABLE course (
    Course_ID INT PRIMARY KEY,
    Course_Name VARCHAR(50),
    Student_ID INT,
    FOREIGN KEY (Student_ID) REFERENCES student(Student_ID)
);
INSERT INTO course VALUES (601, 'DATA 601', 1);   -- ok
INSERT INTO course VALUES (602, 'DATA 602', 1);   -- ok: FK values can repeat
INSERT INTO course VALUES (603, 'DATA 603', 5);   -- ❌ no student 5

Referential integrity: every reference must point at something real (no orphans). Create the referenced table first.

Careful with the slide's "Unique": the side being pointed at (the primary key) is unique; the pointing side (the foreign key) can repeat. One customer, many orders: orders.customer_id → customers.customer_id is one-to-many.

Design note: the slide's course table holds one Student_ID per row, so one student per course. Real enrolment is many-to-many, handled with a middle table: enrolment(Student_ID FK, Course_ID FK) with the composite primary key (Student_ID, Course_ID).

9.4Joining on a condition, and natural joins

SELECT * FROM left_table JOIN right_table
ON (left_table.x = right_table.a);

With x = 1, 3 and a = 1, 2, only x1–a1 matches: 1 row. Add a = 3 on the right and x2 finds a partner: 2 rows. JOIN, INNER JOIN and CROSS JOIN ... ON behave the same in MariaDB; write JOIN ... ON for clarity.

SELECT c.customer_id, o.order_id                 -- table aliases c and o
FROM customers c JOIN orders o ON c.customer_id = o.customer_id;

Without the c. prefix in SELECT you get "Column 'customer_id' in field list is ambiguous": both tables have it.

SELECT * FROM left_table NATURAL JOIN right_table;
-- = SELECT l.id, l.y, r.b FROM left_table AS l JOIN right_table AS r ON l.id = r.id;
NATURAL JOINJoins on every column name the tables share, and shows that column once. Quick for exploring.
The riskTwo shared names (e.g. customer_id and created_date) means joining on both, so most rows vanish with no error. A column added later can silently change it. In real work, write the ON.

9.7Keys in practice (Databricks, night Lecture 6)

Keep the key in your results. Both queries below total licences per animal per community, but only the second says which total is which:

SELECT SUM(`LICENSE VOLUME`) AS total                         -- numbers with no labels
FROM workspace.default.licensed_pets
GROUP BY ANIMAL, `COMMUNITY NAME`;

SELECT ANIMAL, `COMMUNITY NAME`, SUM(`LICENSE VOLUME`) AS total  -- labelled, joinable
FROM workspace.default.licensed_pets
GROUP BY ANIMAL, `COMMUNITY NAME`;
Remember: whatever you GROUP BY is the key of the result, so SELECT it too. A CTE without the community name has nothing to put in a later ON, so it can't be joined.

A counter key with ROW_NUMBER (Databricks has no AUTO_INCREMENT). Use ROW_NUMBER, not RANK: a key must be unique, and RANK repeats on ties. Order by columns that uniquely identify each row, so the numbers don't change between runs.

-- Build a key: add a column, give every row a unique value (rebuild with CTAS,
-- since UPDATE can't use window functions), then declare it
CREATE OR REPLACE TABLE workspace.default.pets_keyed AS
SELECT ROW_NUMBER() OVER (ORDER BY `COMMUNITY NAME`, ANIMAL, my_date) AS pet_row_id, *
FROM workspace.default.licensed_pets;

ALTER TABLE workspace.default.pets_keyed ALTER COLUMN pet_row_id SET NOT NULL;      -- 1st
ALTER TABLE workspace.default.pets_keyed ADD CONSTRAINT pets_pk PRIMARY KEY (pet_row_id);  -- 2nd
ALTER TABLEChange an existing table.
SET NOT NULL firstA primary key can't have blanks, so Databricks refuses the key until the column is NOT NULL.
ADD CONSTRAINT pets_pkNames the rule so you can find or drop it later.
CTASCREATE TABLE ... AS SELECT builds a table from a query. Common in Databricks and Fabric.
MariaDBPrimary keys are enforced: a duplicate ID is rejected.
DatabricksPrimary and foreign keys are informational only: a duplicate 7 is accepted. NOT NULL is enforced but only blocks blanks, not duplicates. Checking billions of rows on every load would be too slow (a BASE-style trade-off).

Keeping keys clean in Databricks anyway: NOT NULL already blocks blanks. For duplicates, (1) let Databricks number the rows with an identity column, which nobody can type their own values into; (2) load with MERGE INTO, which only inserts keys that aren't already there; (3) run the duplicate check below as a safety net.

CREATE TABLE workspace.default.pets_ids (
  pet_row_id BIGINT GENERATED ALWAYS AS IDENTITY,
  community STRING, animal STRING, volume INT
);

MERGE INTO workspace.default.pets_keyed AS t
USING new_rows AS s
ON t.pet_row_id = s.pet_row_id
WHEN NOT MATCHED THEN INSERT *;          -- existing keys are skipped
-- So check uniqueness yourself after loading: should return no rows
SELECT pet_row_id, COUNT(*) FROM workspace.default.pets_keyed
GROUP BY pet_row_id HAVING COUNT(*) > 1;

9.8FULL OUTER JOIN, and which table's column to show

Left_table (X, Y)       Right_table (A, B)        ON Left_table.X = Right_table.A
1 str                   1  sws                    → only 1 matches
2 rtd                   5  was
3 der                   10 qwe
JoinRowsWhich
INNER11 str · 1 sws

FULL OUTER = LEFT + RIGHT combined. Row count = matches + unmatched left + unmatched right (when each match pairs one row with one row). For example, 4 left, 3 right, 2 matching: 2 + 2 + 1 = 5 (= 4 + 3 − 2). Databricks supports it; MariaDB doesn't (use UNION of a LEFT and a RIGHT join there).

Real example: pets_by_community (p: community, total_licences…) joined to community_info (c: community, SECTOR, CLASS).

SELECT p.community, c.SECTOR, c.CLASS, p.total_licences      -- LEFT: every p row kept, so p.community is always filled
FROM workspace.default.pets_by_community AS p
LEFT JOIN workspace.default.community_info AS c ON p.community = c.community
ORDER BY p.total_licences DESC;

SELECT c.community, c.SECTOR, c.CLASS, p.total_licences      -- RIGHT: switch to c.community
FROM workspace.default.pets_by_community AS p
RIGHT JOIN workspace.default.community_info AS c ON p.community = c.community
ORDER BY p.total_licences DESC;

SELECT COALESCE(c.community, p.community) AS community,     -- FULL: either side may be blank
       c.SECTOR, c.CLASS, p.total_licences
FROM workspace.default.pets_by_community AS p
FULL OUTER JOIN workspace.default.community_info AS c ON p.community = c.community
ORDER BY p.total_licences DESC;
Remember: take the key column from the table whose rows are all kept. After a RIGHT join, a community with no pet data has a blank p.community, so show c.community. After a FULL join either side can be blank, so COALESCE(c.community, p.community) takes the first one that isn't.

Join on the key when you can. Both tables have a comm_code (CGR, PAT…). Joining on the code is safer than joining on the name text, where one table's spelling, spacing or capitals could differ and silently drop matches.
